# Qbix proxy — Structural Security Proxy for PHP

A lightweight HTTP proxy that sits between the internet and PHP-FPM, structurally sanitizing every inbound request so PHP's parsers never see attacker-crafted bytes. ~160KB static binary, zero dependencies, deploys in under a minute.

## The problem

On October 21 2026, two critical remote code execution vulnerabilities were disclosed in PHP core:

- **[CVE-2026-109618](https://sansec.io/research/php2shell)** — heap use-after-free in the `session.upload_progress` handler
- **[CVE-2026-109619](https://sansec.io/research/php2shell)** — heap use-after-free in the multipart form-data parser

Both are rated **CVSS 9.2+** and allow unauthenticated remote code execution over the network. They affect **every PHP version from 5.4 onward**. Only PHP 8.2+ will receive official patches; PHP 5.x, 7.x, 8.0, and 8.1 are end-of-life and will not be patched. Researchers have dubbed this pair **"php2shell"** because the attack path goes from a crafted HTTP request straight to a shell on the server.

These are not the first critical parser vulnerabilities in PHP — CVE-2024-2756, CVE-2024-3096 (multipart parser), CVE-2024-11236 (session upload progress), and CVE-2026-6722 (SOAP use-after-free, CVSS 9.5) follow the same pattern. The underlying issue is structural: PHP's C-level HTTP parsers handle raw attacker-controlled bytes with complex, stateful code that has repeatedly proven vulnerable.

**Discussion:** [Hacker News thread](https://news.ycombinator.com/item?id=50172041) · [Sansec research writeup](https://sansec.io/research/php2shell) · [Forbes coverage](https://www.forbes.com/sites/daveywinder/2026/10/21/critical-php-security-warning-issued-apply-emergency-patch-today/) · [Phoenix Security analysis](https://phoenix.security/php-core-rce-cve-2026-109618-109619-critical-remote-code-execution/) · [Chainguard PHP image tracker](https://cve.chainguard.dev/directory/image/php/vulnerabilities)

## What Qbix proxy does about it

Traditional WAFs use signature matching — they maintain databases of known attack patterns and try to match inbound traffic against them. This approach misses novel exploits by definition, since the signatures don't exist until after the vulnerability is discovered and analyzed.

Qbix proxy takes a fundamentally different approach: **structural sanitization**. It fully parses every inbound HTTP request, validates it against strict structural rules, then re-serializes the request from the parsed representation and forwards only the clean, proxy-generated bytes. The backend never sees the original wire format. There are no signatures to update.

This means:

- Exploits that depend on **malformed multipart boundaries** are eliminated, because the multipart body is re-serialized with a new random boundary generated by Qbix proxy.
- Exploits that depend on **parser differentials** between a WAF and PHP are eliminated, because PHP receives bytes that Qbix proxy generated, not bytes the attacker sent.
- **Request smuggling** via duplicate Content-Length, mixed Content-Length + Transfer-Encoding, or other ambiguous framing is rejected before it reaches the backend.
- Future, as-yet-unknown parser vulnerabilities in PHP are mitigated by the same mechanism — the attacker cannot control the byte-level representation that PHP parses.

### 6-stage validation pipeline

1. **Content-Type validation** — reject unknown or malformed types
2. **Method validation** — configurable allowed methods per backend
3. **Multipart re-serialization** — the core security invariant: multipart bodies are fully parsed, validated (file count, size, extensions, MIME types), then re-serialized with a new random boundary. The backend receives a structurally identical but byte-different body.
4. **JSON validation** — configurable depth and string size limits
5. **URL-encoded body validation** — re-serialized from parsed key-value pairs
6. **Header sanitization** — reject non-ASCII header names, NULL bytes, bare CR/LF, duplicate Content-Length, mixed Content-Length + Transfer-Encoding

### Additional protections

- Path traversal blocking (`/../` sequences)
- Chunked transfer decoding and re-validation
- Configurable size limits (body, headers, URL, query params)
- Per-backend routing and constraints
- Prometheus metrics at `/Q/metrics`

### What it is not

- Not a WAF — no signature database, no rules to update
- Not a TLS terminator — sits behind nginx/caddy
- Not a load balancer — forwards to one matched backend per request

The fastest way to get protected is the included PHP setup helper. It detects your web server and PHP-FPM configuration automatically, shows you a colored preview of every change before touching anything, then downloads the binary, patches your configs, and installs a systemd service — all with a rollback-safe backup at each step:

```bash
# Download the helper
curl -LO https://raw.githubusercontent.com/Qbix/proxy/main/qbixproxy-setup.php

# Step 1: Preview — reads nothing, writes nothing, no root needed
php qbixproxy-setup.php

# Step 2: Apply
sudo php qbixproxy-setup.php
```

The helper supports **nginx**, **Apache**, and **Caddy**, and follows the Debian `sites-available` / `sites-enabled` symlink pattern automatically. If the web server's own config test (`nginx -t`, `apachectl -t`, `caddy validate`) fails after patching, the original config is restored from the `.bak` backup and no reload happens.


## Installing manually

If you prefer to download the binary yourself, or want to understand what the helper installs, here are the options.

### Option 1: Download a release binary

Download from the [Releases](../../releases) page:

| Binary | Platform | Notes |
|--------|----------|-------|
| `qbixproxy-linux-x86_64` | Linux x86_64 | Static, ~160KB, zero dependencies |
| `qbixproxy-linux-aarch64` | Linux ARM64 | Static, for AWS Graviton / Ampere / RPi |

Both are statically linked with musl — zero shared library dependencies, run on any Linux system.

Verify the checksum against `SHA256SUMS` in the release.

```bash
# Linux x86_64
curl -LO https://github.com/Qbix/proxy/releases/latest/download/qbixproxy-linux-x86_64
chmod +x qbixproxy-linux-x86_64
./qbixproxy-linux-x86_64 --help

# Linux ARM64 (AWS Graviton, Ampere, Raspberry Pi)
curl -LO https://github.com/Qbix/proxy/releases/latest/download/qbixproxy-linux-aarch64
chmod +x qbixproxy-linux-aarch64
./qbixproxy-linux-aarch64 --help
```

### Option 2: Build from source

```bash
# Prerequisites: gcc (any recent version)
make                # Dynamic-linked binary (development)

# For a static, zero-dependency binary:
sudo apt install musl-tools
make static         # build/qbixproxy-static (~160KB)

# For a cross-platform Cosmopolitan APE binary:
make cosmo          # build/qbixproxy.com (requires cosmocc in PATH)

make clean          # remove build artifacts
```

### Option 3: Deploy as part of Qbix PHP Webserver

This repo is designed to also be a build target in the [Qbix PHP Webserver](https://github.com/Qbix/webserver) repo, where it compiles alongside the full webserver. Qbix proxy uses stub files to exclude features not needed in proxy-only mode (TLS, HTTP/2, WebSocket, PHP embedding, static file serving).

## Quick start (manual)

If you prefer to configure your web server by hand, or want to understand what the automated helper does, here are the manual steps.

1. Create a config file (or copy `examples/qbixproxy.json`):

```json
{
  "backends": {
    "php": {
      "socket": "/run/php/php-fpm.sock",
      "protocol": "fastcgi",
      "document_root": "/var/www/html",
      "routes": ["/"],
      "constraints": {
        "max_body_bytes": 8388608,
        "allowed_methods": ["GET", "POST", "PUT", "DELETE", "HEAD", "OPTIONS"],
        "upload": {
          "max_files": 20,
          "max_file_bytes": 10485760,
          "allowed_extensions": [".jpg", ".png", ".pdf", ".zip"]
        }
      }
    }
  }
}
```

2. Start Qbix proxy:

```bash
./qbixproxy-linux-x86_64 --config=qbixproxy.json --port=8080
```

3. Point your reverse proxy (nginx, caddy) at Qbix proxy instead of PHP-FPM directly:

```
Internet → nginx (TLS) :443 → qbixproxy :8080 → php-fpm.sock
```

nginx config:
```nginx
upstream qbixproxy {
    server 127.0.0.1:8080;
}
server {
    listen 443 ssl;
    location / {
        proxy_pass http://qbixproxy;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## Security hardening

Qbix proxy doesn't read or write any files at runtime — it receives bytes on a socket, sanitizes them in memory, and forwards them to a backend socket. It doesn't need access to your document root, your PHP files, your uploads directory, or anything else on disk. Run it as a dedicated user with no privileges:

```bash
# Create a no-login, no-home user
sudo useradd --system --no-create-home --shell /usr/sbin/nologin qbixproxy

# The binary and config are the only files it needs to read
sudo chown root:root /usr/local/bin/qbixproxy
sudo chown root:root /etc/qbixproxy/qbixproxy.json

# Run it
sudo -u qbixproxy /usr/local/bin/qbixproxy --config=/etc/qbixproxy/qbixproxy.json --port=8080
```

If you're using systemd (the deployment guides include ready-made service files), the service runs as this user automatically. You can go further with `ProtectSystem=strict`, `ProtectHome=yes`, `NoNewPrivileges=yes`, and `CapabilityBoundingSet=` to drop all capabilities — Qbix proxy doesn't need any. If the proxy is ever compromised, the attacker has a process that can open network sockets and nothing else.

### Already protected: Qbix PHP Webserver

The [Qbix PHP Webserver](https://github.com/Qbix/webserver) is **not vulnerable to php2shell** out of the box. It has Qbix proxy's sanitization pipeline compiled directly into its request-handling path — every request is structurally sanitized before PHP-FPM receives it, with zero configuration and no extra process. If you're already running the Qbix webserver, you're already protected.

nginx, Apache, and Caddy don't parse multipart request bodies — they have no reason to look inside the body, so they pass the raw bytes straight through to PHP. That's exactly what php2shell exploits. The Qbix webserver parses and re-serializes those bytes before PHP ever sees them, the same way Qbix proxy does.

The Qbix webserver also handles TLS (with automatic certificate management), virtual hosting, static file serving, and HTTP/2 — so there's no reverse proxy to configure and fewer moving parts overall. If you're currently running nginx or Apache just to sit in front of PHP-FPM, it's worth a look: [github.com/Qbix/webserver](https://github.com/Qbix/webserver).

### Configuration reference

Backend fields:

| Field | Description |
|-------|-------------|
| `socket` | Unix socket path to the backend |
| `protocol` | `fastcgi` (default) or `http` |
| `document_root` | Passed as `DOCUMENT_ROOT` to FastCGI |
| `routes` | URL prefixes this backend handles |
| `constraints` | Validation limits (see `examples/qbixproxy.json` for all options) |

CLI flags:

```
--config=FILE    JSON config file (required)
--port=N         Listen port (default: 8080)
--host=ADDR      Bind address (default: 0.0.0.0)
--root=DIR       Document root
--threads=N      Event loop threads (default: one per CPU core)
--access-log=F   Combined-format access log
--max-post=N     Max POST body in bytes
-t               Test config and exit
```

## Architecture

```
                    ┌─────────────────────────────────────┐
 Client request  →  │  HTTP Parser (http.c)                │
                    │  • smuggling detection                │
                    │  • header injection prevention        │
                    ├─────────────────────────────────────┤
                    │  Sanitizer (sanitize.c)               │
                    │  1. Content-Type check                │
                    │  2. Method check                      │
                    │  3. Multipart re-serialize            │
                    │  4. JSON depth/size check             │
                    │  5. URL-encoded re-serialize          │
                    │  6. Header sanitize                   │
                    ├─────────────────────────────────────┤
                    │  Proxy (proxy.c)                      │
                    │  • backend matching                   │
                    │  • FastCGI or HTTP forwarding         │
                    │  • response sanitization              │
                    └─────────────────────────────────────┘
                                    ↓
                         Backend (PHP-FPM / HTTP)
```

## Trust and transparency

The entire Qbix proxy is **~3,500 lines of C** across 20 source files. There are no external dependencies beyond libc and pthreads.

**Open source.** The complete source is in `src/`. Read it — that's the point. The code uses `snprintf` and growable buffers (`ubuf`) throughout; there are no calls to `sprintf`, `strcpy`, `strcat`, or `gets`. All memory allocations are bounded by configurable limits.

**Reproducible builds.** Release binaries are built by GitHub Actions from the source in this repo — not on anyone's laptop. The [CI workflow](.github/workflows/ci.yml) builds on every push, and the [release workflow](.github/workflows/release.yml) builds, verifies, and publishes binaries when a version tag is pushed. You can inspect the build logs for any release.

**Build it yourself.** If you don't trust the pre-built binaries, building from source takes one command:

```bash
sudo apt install musl-tools   # one-time setup
make static                    # produces build/qbixproxy-static (~160KB)
```

The static binary has zero shared library dependencies and runs on any Linux system.
